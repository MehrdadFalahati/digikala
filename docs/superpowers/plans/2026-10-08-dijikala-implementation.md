# DijiKala Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a runnable educational marketplace where sellers manage stores and products, and customers purchase from multiple stores using a simulated wallet.

**Architecture:** Use one Django project with four focused apps: `accounts`, `shops`, `cart`, and `orders`. Render Persian HTML templates on the server and use PostgreSQL for development and tests. Keep payment calculations and wallet transfers in transactional services, with ownership enforced on the server.

**Tech Stack:** Python 3.12, Django 5.2 LTS, PostgreSQL 17, Psycopg 3, Pillow, python-dotenv, Django's test framework, HTML, CSS, and Docker Compose for the local database. Pin compatible patched dependency versions when implementation begins.

**Spec:** [Design specification](../specs/2026-10-08-dijikala-design.md). The user requested this implementation plan after requiring PostgreSQL; the plan is ready for review, and no application code has been written.

## Global Constraints

- Use PostgreSQL for both application data and tests, as required by the course.
- Use Django's built-in `User`, with separate `CustomerProfile` and `SellerProfile` models.
- Support multiple stores per seller, with exactly one seller owning each store.
- Preserve `/`, `/stores/`, `/stores/<id>/`, `/seller/`, `/customer/`, `/cart/`, `/payment/`, `/orders/`, `/orders/<id>/`, `/accounts/signup/`, `/accounts/login/`, `/accounts/logout/`, and `/admin/`.
- Display money in toman and calculate it with `Decimal`; never use floating-point arithmetic for money.
- Treat wallet top-ups and purchases as simulations; no banking integration is required.
- Keep the interface Persian, right-to-left, and responsive.
- Require POST and CSRF protection for mutations, including logout.
- Restrict customers to their own cart, wallet, and orders; restrict sellers to their own stores and products.
- Record immutable purchase-time product names and prices; protect purchased products and stores from deletion.
- Apply all checkout changes in one transaction, including wallet transfers, stock changes, order creation, and cart clearing.
- Acquire checkout locks in this order: customer profile, products ordered by primary key, then stores ordered by primary key.
- Keep database credentials in environment variables; exclude `.env`, uploaded media, and local artifacts from Git.
- Include search, categories, image uploads, stock management, and a thank-you page as the proposed optional-credit features. Core marketplace behavior remains the first priority.
- Provide migrations, repeatable demo data, and a complete local setup guide.
- Initialize a local Git repository if one is still absent at execution time. Task commits are local checkpoints; repository publication is a separate action.

## Review Focus

1. A forged store, customer, or order ID must not expose or modify another user's data. Covered in Tasks 2, 3, 4, and 6.
2. Repeated or stale checkout submissions must not charge twice or purchase a different cart accidentally. Covered in Tasks 4 and 6.
3. Non-finite, oversized, negative, or excessively precise monetary inputs must fail before changing balances. Covered in Tasks 3, 5, and 6.
4. Concurrent purchases must not oversell the last unit, overdraw a wallet, or lose a store credit. Covered in Task 6.
5. Invalid images and malformed search/category parameters must produce readable errors rather than server failures. Covered in Task 7.

## Shared Implementation Decisions

- Money fields use `DecimalField(max_digits=14, decimal_places=2)`. The supported maximum is `999999999999.99` toman. Reject non-finite values and values requiring more than two decimal places rather than silently rounding financial inputs.
- Profiles relate one-to-one to `settings.AUTH_USER_MODEL`. Store owners reference `SellerProfile`; carts and orders reference `CustomerProfile`.
- Add `CustomerProfile.checkout_key`, a UUID generated on profile creation and rotated after each successful cart mutation. Add a unique `Order.checkout_key` to identify completed checkouts.
- Customer ID in service signatures means `CustomerProfile.pk`, not `User.pk`.
- `CartItem(customer, product)` is unique. Cart quantities are positive; product stock is nonnegative. Enforce these invariants in forms and database constraints.
- `OrderItem` stores `product_name`, `unit_price`, `quantity`, and a protected reference to both the product and the store. Orders and line items are read-only in the admin; prevent financial edits through ordinary admin forms.
- Every cart mutation locks the customer profile before accessing the cart. It may read product availability but does not reserve stock; checkout rechecks locked product rows.
- Views derive profile IDs from the authenticated user. Customer and owner IDs supplied by the browser are never trusted.
- Nonfinancial profile/store edits, including admin saves, must update only editable fields and never write a previously loaded balance. Product stock edits must load and update the product within a row-locked transaction; immutable store ownership is excluded from the product form.
- Service validation errors use stable codes and Persian messages. Views convert them into form errors or Django messages; an unauthorized role receives HTTP 403 and an inaccessible object receives HTTP 404.
- Product/store deletion is outside the seller UI's required scope. Purchased records are protected at the model level.
