# طرح پیشنهادی پروژه DijiKala

وضعیت: پیش‌نویس برای بررسی کاربر؛ پیاده‌سازی هنوز شروع نشده است.

## هدف و منبع نیازمندی‌ها

درخواست کاربر: پیاده‌سازی پروژه با Python و Django. طبق توضیح بعدی کاربر، استفاده از PostgreSQL الزام دوره است و پایگاه دادهٔ پروژه باید PostgreSQL باشد.

منبع مشخصات: سه صفحهٔ فایل `HW_L5_01_Django[DijiKala].pdf`.
هدف، یک بازارگاه کوچک آموزشی با فروشندگان، مشتریان، سبد خرید و پرداخت آزمایشی است.
پوشهٔ فعلی خالی است و مخزن Git یا قالب آماده ندارد.
دستورهای مربوط به ارسال لینک GitHub و پرسیدن سؤال در تلگرام، دستورهای تحویل تمرین هستند؛ این طرح آن‌ها را درخواست انتشار یا ارسال پیام از طرف کاربر تلقی نمی‌کند.

## رویکردهای قابل انتخاب

1. **پیشنهاد: Django با قالب‌های HTML و PostgreSQL.** مدل‌ها، فرم‌ها، نماها و پنل مدیریت در یک پروژه قرار می‌گیرند. ساختار برای تمرین قابل مطالعه است و الزام پایگاه دادهٔ دوره را رعایت می‌کند.
2. **API در Django با PostgreSQL و رابط جداگانه.** برای کلاینت‌های متعدد کاربرد دارد، اما پیچیدگی احراز هویت، استقرار و توسعهٔ رابط را افزایش می‌دهد و تمرین چنین الزامی ندارد.

طرح زیر بر اساس گزینهٔ اول نوشته شده است. انتخاب نسخهٔ قابل نصب و سازگار Django هنگام پیاده‌سازی انجام می‌شود؛ شاخهٔ 5.2 LTS گزینهٔ اولیه است.

## پایگاه داده و راه‌اندازی محلی

- PostgreSQL پایگاه دادهٔ توسعه و آزمون است.
- پیشنهاد راه‌اندازی: PostgreSQL 17 با Docker Compose، فضای ذخیره‌سازی پایدار و بررسی سلامت سرویس؛ برنامهٔ Django در محیط مجازی Python اجرا می‌شود.
- اگر PostgreSQL از قبل نصب شده باشد، اتصال به همان سرویس با تغییر تنظیمات محیطی امکان‌پذیر است.
- اتصال Django از درایور Psycopg استفاده می‌کند؛ وابستگی سازگار هنگام پیاده‌سازی مشخص می‌شود.
- نام پایگاه داده، میزبان، درگاه، کاربر و رمز از متغیرهای محیطی خوانده می‌شوند. فایل `.env.example` نام متغیرها و مقادیر نمونهٔ محلی را مستند می‌کند؛ فایل `.env` در Git قرار نمی‌گیرد.
- راهنمای اجرا شامل راه‌اندازی سرویس، اجرای migrationها، ساخت ادمین، افزودن دادهٔ نمونه و اجرای آزمون‌هاست.

## محدودهٔ اصلی مطابق تمرین

| مسیر | رفتار |
| --- | --- |
| `/` | نمایش محصولات از جدید به قدیم؛ لینک فروشگاه‌ها، ورود و ثبت‌نام؛ نمایش سبد برای مشتری واردشده |
| `/stores/` | فهرست همهٔ فروشگاه‌ها و لینک صفحهٔ هر فروشگاه |
| `/stores/<id>/` | محصولات فروشگاه؛ نمایش دکمهٔ افزودن محصول فقط به مالک |
| `/seller/` | فروشگاه‌های فروشندهٔ فعلی، ایجاد فروشگاه و دسترسی به مدیریت آن‌ها |
| `/customer/` | نام، شماره تلفن، شناسهٔ حساب و موجودی؛ لینک شارژ، سبد و سفارش‌ها |
| `/cart/` | اقلام، تعداد، مبلغ و حذف؛ پرداخت آزمایشی |
| `/payment/` | فرم افزایش موجودی مشتری با مبلغ مثبت |
| `/orders/` | تاریخچهٔ سفارش‌های مشتری فعلی |
| `/orders/<id>/` | جزئیات سفارش متعلق به مشتری فعلی |
| `/accounts/signup/` | ثبت‌نام با انتخاب نقش مشتری یا فروشنده |
| `/accounts/login/` | ورود با نام کاربری و رمز عبور |
| `/accounts/logout/` | خروج با درخواست POST |
| `/admin/` | مدیریت کاربران، فروشگاه‌ها، محصولات و سفارش‌ها برای کارکنان مجاز |

مسیرهای ایجاد/ویرایش فروشگاه و محصول و تغییر سبد زیر مجموعهٔ همین اپ‌ها تعریف می‌شوند. شناسه‌های نامعتبر یا متعلق به کاربران دیگر اطلاعات خصوصی را نمایش نمی‌دهند.

## فرض‌های پیشنهادی

- ثبت‌نام مشتری و فروشنده جداست. هر فروشنده می‌تواند چند فروشگاه داشته باشد و هر فروشگاه یک مالک دارد؛ این انتخاب با مدل پیشنهادی تمرین سازگار است.
- شناسهٔ مشتری، شناسهٔ حساب در پایگاه داده است؛ تمرین فیلد کد ملی تعریف نکرده است.
- مبالغ در رابط به تومان نمایش داده می‌شوند. همهٔ محاسبات سمت سرور با نوع Decimal انجام می‌شود.
- پرداخت و شارژ کاملاً آزمایشی هستند و درگاه بانکی لازم ندارند.
- رابط فارسی و راست‌به‌چپ است. چون قالب‌های اشاره‌شده در PDF در پوشه موجود نیستند، قالب‌های ساده و واکنش‌گرا ساخته می‌شوند.
- امکانات امتیازی پیشنهادی: جست‌وجو، دسته‌بندی، تصویر محصول، موجودی کالا و صفحهٔ تشکر. این‌ها در PDF اختیاری هستند و در این طرح به‌عنوان پیشنهاد اضافه شده‌اند.

## ساختار پیشنهادی

- `config`: تنظیمات، URL اصلی و نقطهٔ ورود برنامه.
- `accounts`: ثبت‌نام، پروفایل مشتری/فروشنده، پنل مشتری و شارژ آزمایشی.
- `shops`: فروشگاه، دسته‌بندی، محصول، صفحات عمومی و مدیریت فروشنده.
- `cart`: اقلام سبد و عملیات افزودن، تغییر تعداد و حذف.
- `orders`: سفارش‌ها، تاریخچه و سرویس پرداخت آزمایشی.
- `templates` و `static`: قالب مشترک، صفحات فارسی و CSS مشترک.
- فایل راهنمای اجرا، وابستگی‌ها، migrationها و فرمان تولید دادهٔ نمونه برای نمایش پروژه.

این اپ‌ها مسئولیت‌های مشخص دارند. انتقال موجودی و ثبت سفارش فقط از سرویس پرداخت در `orders` انجام می‌شود.

## مدل‌ها

| مدل | داده‌ها و قواعد |
| --- | --- |
| `User` | کاربر داخلی Django؛ ذخیره و اعتبارسنجی رمز با سازوکار خود Django |
| `CustomerProfile` | ارتباط یک‌به‌یک با کاربر، تلفن و موجودی غیرمنفی |
| `SellerProfile` | ارتباط یک‌به‌یک با کاربر |
| `Store` | نام، توضیحات، مالک فروشنده و موجودی غیرمنفی |
| `Category` | نام و شناسهٔ خوانا، برای امکان اختیاری دسته‌بندی |
| `Product` | نام، توضیحات، قیمت مثبت، تصویر اختیاری، فروشگاه، دستهٔ اختیاری، موجودی غیرمنفی و زمان ایجاد |
| `CartItem` | مشتری، محصول و تعداد مثبت؛ هر محصول فقط یک ردیف در سبد هر مشتری دارد |
| `Order` | مشتری، جمع مبلغ و زمان ثبت |
| `OrderItem` | سفارش، محصول، فروشگاه، تعداد و قیمت زمان خرید؛ نگهداری نام محصول برای تاریخچه |

فیلد `Store.balance` در جدول مدل‌های PDF نیامده، ولی رفتار پرداخت در همان PDF به آن نیاز دارد و در این طرح اضافه شده است.
حذف محصول یا فروشگاهِ استفاده‌شده در سفارش نباید تاریخچهٔ خرید را از بین ببرد؛ ارتباط‌های سفارش محافظت می‌شوند.
تغییر قیمت یا نام محصول پس از خرید، نام و مبلغ ثبت‌شده در سفارش را تغییر نمی‌دهد.

## دسترسی و فرم‌ها

- مشاهدهٔ فروشگاه و محصول عمومی است.
- عملیات سبد، شارژ و سفارش به مشتری واردشده محدود می‌شود.
- ساخت و مدیریت فروشگاه به فروشنده واردشده محدود می‌شود؛ مالکیت هنگام هر درخواست در سرور بررسی می‌شود.
- فروشندهٔ دیگر حتی با تغییر URL یا دادهٔ فرم نمی‌تواند محصول یا فروشگاه دیگری را ویرایش کند.
- فیلد مالک و موجودی فروشگاه از ورودی فرم فروشنده پذیرفته نمی‌شوند.
- ثبت‌نام عادی اجازهٔ انتخاب نقش ادمین یا دسترسی کارکنان نمی‌دهد.
- تغییر داده‌ها با POST و حفاظت CSRF انجام می‌شود. مبلغ، قیمت، تعداد و فایل تصویر در سرور اعتبارسنجی می‌شوند.
- نام کاربری تکراری، مبلغ نامعتبر، سبد خالی، موجودی ناکافی کیف پول و کمبود کالا پیام قابل فهم دارند.

## جریان خرید آزمایشی

1. سرویس پرداخت در یک تراکنش، ردیف پروفایل مشتری فعلی را قفل می‌کند و اقلام سبد او را دریافت می‌کند. عملیات تغییر سبد همان قفل مشتری را رعایت می‌کنند تا سبد وسط پرداخت تغییر نکند.
2. ردیف محصولات و فروشگاه‌های مربوط قفل می‌شوند و قیمت و موجودی معتبر از پایگاه داده خوانده می‌شود؛ مبلغ ارسال‌شده از مرورگر مبنای خرید نیست.
3. مبلغ سفارش محاسبه و کافی بودن موجودی مشتری و کالا بررسی می‌شود.
4. در همان تراکنش، موجودی مشتری کم می‌شود، سهم هر فروشگاه به موجودی همان فروشگاه اضافه می‌شود، موجودی کالا کم می‌شود و سفارش و ردیف‌های آن ثبت می‌شوند.
5. سبد پس از ثبت موفق سفارش خالی و مشتری به صفحهٔ تشکر/جزئیات سفارش منتقل می‌شود.
6. هر خطا در این مراحل، همهٔ تغییرهای آن پرداخت را برمی‌گرداند؛ خرید ناقص یا انتقال جزئی پول ثبت نمی‌شود.

به‌روزرسانی موجودی‌ها از شرط‌های سمت پایگاه داده و عبارت‌های `F` استفاده می‌کند؛ قیمت و تعداد سفارش در زمان پرداخت تثبیت می‌شوند.
درخواست مجدد همان خرید باید فقط نتیجهٔ همان سفارش را نشان دهد و دوباره موجودی کسر نکند؛ برای این کار شناسهٔ یکتای پرداخت کنترل می‌شود.
قفل‌ها با `select_for_update` داخل `transaction.atomic` روی PostgreSQL گرفته می‌شوند و تا پایان تراکنش نگه داشته می‌شوند. ترتیب اخذ قفل‌ها در مسیرهای مرتبط ثابت است: مشتری، محصولات با ترتیب شناسه، سپس فروشگاه‌ها با ترتیب شناسه. این ترتیب احتمال بن‌بست را کاهش می‌دهد.
خریدهای هم‌زمان روی آخرین موجودی محصول، خریدهای هم‌زمان یک مشتری و افزایش هم‌زمان موجودی فروشگاه با اتصال‌های مستقل به PostgreSQL آزموده می‌شوند.

## معیارهای پذیرش و آزمون‌ها

- مشتری و فروشنده ثبت‌نام و وارد پنل نقش خود می‌شوند.
- فروشنده فروشگاه می‌سازد، محصول اضافه می‌کند و فقط داده‌های خودش را تغییر می‌دهد.
- محصولات جدیدتر ابتدا نمایش داده می‌شوند و صفحهٔ فروشگاه فقط محصولات همان فروشگاه را نشان می‌دهد.
- یک سبد می‌تواند محصول چند فروشگاه را نگه دارد؛ افزودن مجدد تعداد همان ردیف را افزایش می‌دهد.
- شارژ مثبت موجودی را افزایش می‌دهد؛ شارژ صفر، منفی یا نامعتبر پذیرفته نمی‌شود.
- خرید چندفروشگاهی جمع مبلغ را از مشتری کم و سهم درست را به هر فروشگاه اضافه می‌کند.
- موجودی ناکافی کیف پول یا کالا، سفارش یا انتقال پول ناقص ایجاد نمی‌کند و سبد را حفظ می‌کند.
- ارسال تکراری درخواست پرداخت باعث کسر دوباره نمی‌شود.
- دو مشتری نمی‌توانند آخرین واحد یک کالا را هر دو بخرند؛ فقط یک سفارش موفق ثبت می‌شود.
- خریدهای هم‌زمان یک مشتری باعث موجودی منفی یا برداشت تکراری نمی‌شوند.
- خریدهای هم‌زمان از یک فروشگاه، افزایش موجودی فروشگاه را از دست نمی‌دهند.
- مشتری نمی‌تواند سفارش یا سبد مشتری دیگر را ببیند یا تغییر دهد.
- تغییر محصول پس از سفارش، قیمت و نام ثبت‌شدهٔ خرید را تغییر نمی‌دهد.
- آزمون‌های یکپارچهٔ Django برای ثبت‌نام، کنترل دسترسی، سبد، شارژ و پرداخت روی PostgreSQL اجرا می‌شوند؛ آزمون هم‌زمانی از تراکنش‌ها و اتصال‌های مستقل استفاده می‌کند. صفحات اصلی و فرم‌ها نیز بررسی می‌شوند.
- دادهٔ نمونه، راهنمای راه‌اندازی و migrationهای قابل اجرا تحویل داده می‌شوند.

## مستندات بررسی‌شده

مستندات فعلی Django با Context7 و شناسهٔ `/django/django` دریافت شد:

- پروفایل متصل به کاربر داخلی: https://github.com/django/django/blob/main/docs/topics/auth/customizing.md
- تراکنش‌های `transaction.atomic`: https://github.com/django/django/blob/main/docs/topics/db/transactions.md

مستندات PostgreSQL 17 نیز با Context7 و شناسهٔ `/websites/postgresql_17` دریافت شد:

- قفل ردیفی، طول عمر قفل و بن‌بست: https://www.postgresql.org/docs/17/explicit-locking.html
- حفظ سازگاری با قفل‌های صریح: https://www.postgresql.org/docs/17/applevel-consistency.html

در مرحلهٔ پیاده‌سازی، رفتارهای استفاده‌شده با نسخهٔ نصب‌شده و آزمون‌ها تأیید می‌شوند.
